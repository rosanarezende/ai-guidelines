Framework de fluxo governado

ai-guidelines Flow

Transforme decisões de engenharia em um caminho claro: o framework mostra o estado do repo, orienta o próximo passo, protege decisões humanas e registra evidência até o merge final.

Escolha o ponto de entrada certo

O framework não espera que você memorize comandos. Ele separa os cenários reais: projeto novo, projeto existente e repositório que já usa ai-guidelines.

projeto novo

Inicializar do zero

npm run flow -- init

Use quando o diretório ainda não tem governança. O fluxo cria o baseline, configura providers/features e mostra preview antes de escrever.

  • Ideal para começar com práticas padronizadas.
  • Escolha providers e features dentro do próprio fluxo.
  • Dry-run permite ver o plano sem tocar no repo.
repo existente

Adotar sem apagar história

npm run flow -- adopt

Use quando o projeto já existe. O fluxo preserva o que está no repo e adiciona a governança de forma conservadora.

  • Não trata o repo como projeto vazio.
  • Mescla blocos gerenciados quando possível.
  • Explica conflitos antes de qualquer alteração.
repo governado

Usar e atualizar no dia a dia

npm run flow

Use quando o repo já tem ai-guidelines. O wizard mostra o estado, a próxima ação e, quando fizer sentido, oferece update.

  • Update cobre runtime, templates, providers e práticas.
  • Política de colaboração e revisão vem de review-policy.yml.
  • Handoff copia contexto para sua LLM de preferência.
  • Decisões ficam separadas de execução técnica.

Init, adopt e update não são a mesma coisa

O wizard deve mostrar apenas o caminho que faz sentido para o estado do repositório. Isso evita escolhas perigosas e deixa o fluxo mais simples para humanos.

init

Nascimento

Cria uma base governada em um diretório novo.

  • baseline inicial;
  • templates e runtime;
  • providers/features escolhidos no fluxo.
adopt

Entrada em um repo vivo

Adiciona governança a um projeto que já existe.

  • preserva arquivos existentes;
  • faz merge conservador;
  • expõe conflitos de forma clara.
update

Manutenção governada

Atualiza um repo que já usa o framework.

  • runtime e templates;
  • providers via update --providers;
  • práticas como Prettier, Husky, CI, Quality Gates, TDD e BDD;
  • perfil de colaboração e regras de revisão já governadas.

Dois perfis diferentes, duas responsabilidades

O fluxo não mistura “como o repositório colabora” com “que tipo de PR está aberto”. Essa separação evita que uma equipe maior force reviews semânticos por acidente, ou que um projeto solo pareça menos governado.

colaboração

Perfil do repositório

Fonte: .governance/review-policy.yml.

  • solo: projeto mantido por uma pessoa;
  • contributor: recebe contribuições ocasionais;
  • team: equipe com approvals e last-push approval.
PR

Perfil do PR

Fonte: contrato de body/template do PR.

  • execution: implementação;
  • governance: decisão/modelagem;
  • integration: fechamento da stack;
  • fast-track: correção urgente.
reviews

Capacidade não é obrigação

Reviews semânticos são decididos por requisitos explícitos.

  • technical_audit pode existir sem ser obrigatório;
  • security_review pode ser obrigatório só na integração;
  • team não significa “TA obrigatório”.

Fluxo 1 — Inicializar um projeto novo

Use este caminho quando a pasta ainda está vazia ou quando o produto está nascendo junto com a governança. A experiência deve parecer um onboarding guiado, não uma lista de comandos soltos.

A pessoa começa com um diretório vazio

O wizard não pergunta “init, adopt ou update?” sem contexto. Ele explica que este é um projeto novo e coloca inicializar como caminho principal.

  • Não mostra adopt/update como ação principal.
  • Não exige que a pessoa conheça a topologia interna.
  • Oferece dry-run antes da primeira escrita.
npm run flow
┌ ai-guidelines flow ◆Projeto novo detectado │Nenhuma governança local encontrada. ●Inicializar ai-guidelines neste projeto ○Ver preview sem escrever arquivos └ Nada será aplicado sem confirmação.

As escolhas aparecem como grupos

A tela simula o uso de seleção agrupada: providers ficam em um grupo, práticas em outro, e cada item explica o impacto.

  • Providers não voltam como comando separado.
  • Features são escolhas explícitas.
  • O humano entende o que está ligando.
seleção agrupada
◆Escolha canais e práticas iniciais Providers ◾ Claude (AGENTS.md)◾ OpenAI (Codex) Práticas do repo ◾ Prettier (formatação)◾ CI (checks no PR)◻ Husky (hooks locais)

Preview antes de tocar no disco

O init mostra os efeitos planejados: arquivos, blocos gerenciados, templates e orientações. O wizard só apresenta; o plano vem do runtime governado.

  • Dry-run preserva o filesystem.
  • Conflitos aparecem como bloqueios claros.
  • Aplicar exige confirmação explícita.
preview
◇Plano de inicialização │Criar AGENTS.md e configuração local │Espelhar templates e runtime │Adicionar blocos gerenciados ◆Aplicar estas mudanças? ●Sim, aplicar ○Não, manter só o preview

Depois de aplicar, validar vira uma lista de tarefas

A pessoa vê progresso por etapa. Isso fica mais didático do que apenas imprimir um script longo.

  • Checa diff e formatação.
  • Compila o runtime.
  • Orienta o primeiro commit.
validação
◇Validar mudanças iniciais ✓Whitespace do diff ✓Formatação dos arquivos novos ✓Build TypeScript ◆Próximo: revisar o diff e commitar
  1. 1

    Detectar que é um começo limpo

    O flow identifica que ainda não existe governança local e oferece um único caminho principal: inicializar o framework neste projeto.

    • Não mostra update como ação principal.
    • Não oferece o comando antigo providers.
    • Explica que arquivos serão criados antes de escrever qualquer coisa.
  2. 2

    Escolher canais e práticas iniciais

    A pessoa escolhe providers, features e práticas como CI, Prettier ou Husky em uma tela agrupada, com linguagem de produto e sem precisar lembrar flags.

    • Providers ficam dentro do fluxo de init.
    • Features entram como escolhas explícitas, não como efeitos escondidos.
    • O preview mostra o impacto antes da confirmação.
  3. 3

    Ver o plano antes de aplicar

    O wizard mostra o plano de provisionamento: arquivos, blocos gerenciados, templates, runtime e orientações. O dry-run permite testar sem tocar no disco.

    • O plano vem do modelo governado, não do wizard.
    • Conflitos aparecem como bloqueios explicados.
    • Sem confirmação, nada é escrito.
  4. 4

    Aplicar, validar e fazer o primeiro commit

    Depois da confirmação, o framework cria a base governada. Em seguida, orienta a validação mínima e o commit inicial do projeto.

    • O humano vê o que foi criado.
    • As validações aparecem como etapas, não como lista solta de scripts.
    • O repositório já nasce com trilha de governança.
O que a pessoa vê

Um caminho curto: começar, escolher, revisar o preview, confirmar e validar. A pessoa não precisa saber a topologia interna para sair com um repo governado.

projeto novo
npm run flow ou: npm run flow -- init --dry-run depois: npm run flow -- init

Fluxo 2 — Adotar um projeto existente

Use este caminho quando o projeto já tem arquivos, histórico e escolhas próprias. A governança entra por merge conservador, preservando o que já existe.

O repositório não está vazio

O wizard mostra que encontrou arquivos existentes e muda o caminho principal para adoção. Assim a pessoa não precisa saber que init seria arriscado neste cenário.

  • Detecta package.json, workflows, hooks ou arquivos de produto.
  • Oferece adopt como caminho seguro.
  • Mantém dry-run como primeira opção.
npm run flow
┌ ai-guidelines flow ◆Projeto existente detectado │Encontrado package.json e arquivos locais. ●Adotar ai-guidelines neste repositório ○Ver preview conservador └ Init fica fora do caminho principal.

O merge é explicado antes de aplicar

A tela deixa claro quais blocos serão adicionados, quais arquivos serão preservados e onde o humano precisa revisar.

  • Conteúdo existente não é tratado como descartável.
  • Blocos gerenciados entram por marcação clara.
  • Providers e práticas são selecionados dentro de adopt.
preview conservador
◇Plano de adoção ✓Preservar README.md existente ✓Adicionar bloco gerenciado em AGENTS.md ✓Espelhar templates governados │Providers: claude, openai

Conflito vira escolha explícita

Se algo importante já existe, o flow não sobrescreve em silêncio. Ele mostra o conflito e explica quando --force muda o resultado.

  • Sem force, a ação bloqueia com motivo.
  • Com force, o preview precisa mostrar exatamente o que muda.
  • O humano decide, não o adapter.
conflito
▲Conflito encontrado │package.json já define scripts próprios. ◆Como deseja seguir? ●Parar e revisar conflito ○Gerar preview com --force

O onboarding termina com diff verificável

Depois da adoção, o flow orienta uma validação proporcional: checar o diff, formatar quando permitido e compilar.

  • Não precisa rodar smoke de pacote em todo ajuste intermediário.
  • Validação completa continua antes de decisões importantes.
  • O commit registra a adoção como mudança própria.
validar diff
◆Validar mudanças da adoção ✓Diff sem whitespace inválido ✓Arquivos alterados formatados ✓Build verde ●Pronto para revisar e commitar
  1. 1

    Reconhecer que o repo já existe

    O flow detecta sinais como package.json, workflows, hooks, templates ou arquivos de produto. Nesse cenário, o caminho principal é adotar, não inicializar do zero.

    • Init não deve sobrescrever conteúdo por engano.
    • Adopt começa com leitura e preview.
    • Forçar mudanças exige escolha explícita.
  2. 2

    Mapear o que será preservado

    O plano mostra arquivos existentes, blocos gerenciáveis e conflitos. O objetivo é deixar claro o que será mesclado, criado, preservado ou bloqueado.

    • Conteúdo local é preservado quando possível.
    • Conflitos aparecem antes da escrita.
    • O humano decide se usa --force.
  3. 3

    Escolher providers e práticas do repositório

    Providers e features entram dentro de adopt. A pessoa pode ativar práticas como CI, Prettier e Husky sem precisar decorar comandos separados.

    • Providers são seleção de canais, não comando próprio.
    • Práticas entram como features governadas.
    • O plano mantém dry-run e confirmação.
  4. 4

    Aplicar em pequenos blocos verificáveis

    Depois do preview, o adopt aplica somente os efeitos autorizados. O flow orienta a validação do diff e o commit do onboarding.

    • O repo não precisa parecer novo para ser governado.
    • O humano consegue revisar o impacto por arquivo.
    • A adoção deixa trilha explícita do que mudou.
O que a pessoa vê

Um fluxo cuidadoso: entender o repo, preservar o que existe, escolher o que adicionar, ver conflitos e só então aplicar.

projeto existente
npm run flow ou: npm run flow -- adopt --dry-run exemplo: npm run flow -- adopt --providers claude,openai

Fluxo 3 — Usar e manter um repo governado

Use este caminho quando o repositório já vive com ai-guidelines. Aqui o flow vira a entrada diária: mostra estado, orienta a próxima ação, prepara contexto para IA e mantém runtime, templates, providers, práticas e política.

O repo em uso abre no estado atual

O primeiro contato não deve ser uma lista de comandos. A pessoa vê “onde estamos”, “o que está ok”, “o que falta” e “qual é o próximo passo”.

  • Spec, checkpoint, PR, CI e working tree aparecem juntos.
  • Termos internos ficam em segundo plano.
  • O resumo textual continua disponível fora de TTY.
npm run flow
┌ ai-guidelines flow ◇Estado atual │Agora: melhorar UX do flow │PR #43 Draft · CI verde · tree suja ✓Findings fechados ▲Falta finalizar as mudanças locais

Ação principal, alternativa e bloqueios

O wizard precisa deixar claro o que é prioridade. Alternativas aparecem separadas, e bloqueios ficam explicados dentro do contexto da ação.

  • A próxima ação vem do mesmo modelo usado por work.
  • Decisões vêm do mesmo modelo usado por decide.
  • PIT-0011 aparece como alternativa quando recorrente.
menu principal
◆O que você quer fazer? ●Ver resumo completo do estado ◆Finalizar mudanças locais e validar ○ALTERNATIVA: ver percepções recorrentes ○Ver orientação de trabalho / handoff ○Sair

Repo governado usa update, não init/adopt

Quando o framework já está instalado, a seção de manutenção mostra update como caminho principal: runtime, templates, providers, práticas e política.

  • Init/adopt saem do menu principal.
  • Providers ficam em update --providers.
  • CI, Prettier e Husky ficam em update --features.
atualização
◆O que você quer atualizar? ●Runtime e templates ○Providers usados pelo repo ○Práticas: CI, Prettier, Husky ○Política de colaboração e revisões │Preview antes de aplicar.

Decisões importantes continuam protegidas

O flow pode preparar briefing, preview e validação, mas não executa Ready, Human Gate, avanço ou merge sem autoridade humana explícita.

  • Readiness altera só o artefato permitido.
  • Human Gate exige PR Ready, checks e política satisfeitos.
  • Merge final continua no fechamento da spec inteira.
decisão protegida
◇Decisão disponível │Declarar readiness do ponto atual ▲Human Gate ainda bloqueado │Motivo: PR ainda Draft ou critérios faltando ◆Ver briefing antes de decidir? ●Sim, abrir preview
  1. 1

    Abrir o estado do repo

    npm run flow mostra onde o trabalho está: spec ativa, checkpoint, sub-checkpoint, PR, CI, reviews, findings, readiness, working tree e próxima ação.

    • O resumo vem do snapshot governado.
    • O wizard não inventa regra própria.
    • As opções aparecem por intenção humana, não por nome interno.
  2. 2

    Seguir a próxima ação recomendada

    O flow separa prioridade, alternativas e bloqueios. Se houver tree suja, ele orienta validar mudanças; se houver readiness disponível, oferece o fluxo governado; se houver bloqueio, explica o motivo.

    • A recomendação precisa bater com work.
    • Decisões precisam bater com decide.
    • Human Gate, Ready e merge continuam protegidos.
  3. 3

    Preparar contexto para humanos e IA

    O flow oferece handoff, orientação de trabalho e tipos de revisão com texto pensado para copiar e colar na LLM ou enviar para uma pessoa revisora.

    • O handoff evita depender da memória do chat anterior.
    • Reviews são preparadas por tipo e contrato.
    • Nada é publicado sem autorização explícita.
  4. 4

    Atualizar o que já existe

    Em um repo governado, a manutenção fica em update: runtime, templates, providers, features, CI, Prettier, Husky e política governada quando aplicável.

    • Init/adopt deixam de ser o caminho principal.
    • Providers entram como update --providers.
    • Práticas entram como update --features.
  5. 5

    Levar uma spec até o merge final

    O fluxo cobre nascimento da spec, implementação, review, resolution, disposition, readiness, Ready, Human Gate, transição de nó, integração e merge final.

    • Cada transição tem autoridade e efeito permitido.
    • O sistema diferencia ação disponível, bloqueada e proibida.
    • O humano decide os gates; o framework registra evidência.
O que a pessoa vê

Um painel de uso contínuo: entender o estado, seguir o próximo passo, validar mudanças, pedir revisão, atualizar o framework e avançar lifecycle sem depender de memória.

repo em uso
npm run flow npm run flow -- handoff 0024 npm run flow -- work npm run flow -- update --features prettier,husky,ci

Da primeira ideia ao merge final

O valor do ai-guidelines aparece quando uma spec deixa de depender da memória de uma pessoa e passa a seguir estados explícitos, decisões auditáveis e evidências.

1 Nasce a spec Problema, intenção, escopo e topologia entram em artefatos governados.
2 PR Draft cedo O PR vira contêiner de trabalho, não sinal de pronto.
3 Handoff Uma nova sessão recebe fatos, não memória solta.
4 Implementação Sub-checkpoints limitam escopo, validação e autoridade.
5 Reviews Auditorias geram findings reproduzíveis.
6 Correções Resolutions, verification e dispositions fecham o ciclo de review.
7 Readiness O fluxo declara que o ponto está pronto; não é edição manual solta.
8 Ready + Gate PR deixa Draft; Human Gate decide se o checkpoint pode avançar.
9 Próximo nó A stack continua sem merge isolado em main.
10 Merge final O PR de integração fecha a spec inteira.

O fluxo mostra proteção, não só erro

A mesma ação pode estar disponível, bloqueada ou proibida. O framework explica o motivo e aponta o comando correto para entender antes de aplicar.

disponível

Pode seguir

Exemplo: ver percepções recorrentes, validar o diff ou abrir uma decisão pronta.

bloqueada

Existe, mas falta algo

Exemplo: tree suja, CI pendente, readiness ausente ou PR ainda Draft.

proibida

Não deve acontecer agora

Exemplo: Ready, Human Gate, merge ou avanço fora da autorização humana.

Por que desenvolvedores deveriam usar

O framework reduz trabalho invisível: menos decisões perdidas em chat, menos drift entre PR e artefatos, e menos risco de avançar no estado errado.

Contexto portátil

Handoff e orientação de trabalho viram texto copiável para qualquer LLM, sem depender de memória de agente.

Decisão humana preservada

Ready, Human Gate e merge continuam exigindo estado correto, briefing e confirmação.

Automação sem surpresa

Comandos diretos e non-TTY são determinísticos; o wizard só aparece quando há pessoa no terminal.

Comandos diretos para quem já sabe o que quer

O wizard é a porta humana. O registry continua disponível para automação e inspeção.
