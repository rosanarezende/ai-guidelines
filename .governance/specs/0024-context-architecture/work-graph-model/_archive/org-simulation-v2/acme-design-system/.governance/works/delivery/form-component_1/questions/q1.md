# q1 — validação do form: schema declarativo ou regra imperativa?

**Pergunta:** como o consumidor (os MFEs) declara a validação do componente — a forma que a
API pública expõe? Hoje cada MFE reimplementa regras soltas; o componente existe pra padronizar.

## Opções (modo `escolha`) — SEM enviesar

### Opção A — schema declarativo (ex.: `{ email: true, required: true }`)

- **Problema que resolve:** padroniza a validação comum (email/site/telefone) sem cada MFE reimplementar.
- **Benefícios:** previsível · serializável · fácil de documentar e testar.
- **Tradeoffs:** engessa o caso custom.
- **Riscos:** virar uma mini-linguagem se crescer demais.
- **Quando escolher:** a maioria dos campos cai em regras conhecidas.
- **Quando NÃO escolher:** o produto exige validação muito específica por campo.

### Opção B — regra imperativa (`validate(value) => erro?`)

- **Problema que resolve:** cobre qualquer regra com uma função.
- **Benefícios:** flexibilidade total.
- **Tradeoffs:** cada consumidor escreve a sua → volta o problema que o componente quer resolver.
- **Riscos:** divergência entre MFEs; inconsistência no DS.
- **Quando escolher:** regras altamente específicas e variáveis.
- **Quando NÃO escolher:** o objetivo é justamente padronizar.
