Contêiner de revisão

3. Como dividir por PRs?

O mapa V2 não obriga uma divisão; ele mostra as opções para escolhermos uma fronteira revisável.

Opção A · recomendada para agora

PR #44 fecha decisão de modelo + inventário

PR #44 ficaria como contêiner de dogfood de drift + modelagem do lifecycle. O refactor estrutural iria para PR posterior.

  • Inclui: drift-diagnosis-and-repair.
  • Inclui: checkpoint-model-boundaries.
  • Inclui: lifecycle-model-inventory.
  • Não inclui: reorganização pesada de arquivos.
Opção B · PR #44 maior

PR #44 também confronta modelo × código

Mantém mais trabalho no PR atual, mas aumenta risco de repetir o problema do PR #43: uma entrega ampla demais para revisão humana confortável.

  • Inclui inventário e confronto.
  • Adia só o refactor para o próximo PR.
  • Exige revisão externa antes de qualquer split físico.
Opção C · evitar

Um PR gigante para toda a continuação

Fechar inventário, refactor, BDD visual, falsificação e review no mesmo PR recria exatamente o custo cognitivo que motivou esta discussão.

  • Difícil de revisar.
  • Mais chance de drift entre narrativa, código e mapa.
  • Human Gate vira grande demais.
Alternativa por checkpoint

Um checkpoint por PR a partir daqui

Mais seguro para revisão, mas pode criar PRs pequenos demais. Útil quando o checkpoint muda arquitetura ou modelo de autoridade.

  • PR #45: confronto modelo × código.
  • PR #46: refactor estrutural.
  • PR #47: BDD visual + falsificação.

4. Regras de modelagem propostas

Estas regras explicam quando um PR pode conter mais de um checkpoint e quando isso vira risco.

Pergunta Regra proposta Impacto no PR #44
Um PR pode conter mais de um checkpoint? Sim, quando os checkpoints são pequenos, sequenciais, acoplados e revisáveis como uma entrega coesa. PR #44 pode conter drift + decisão de modelo + inventário, se o refactor ficar fora.
Um checkpoint pode atravessar mais de um PR? Normalmente não. Se precisa atravessar, o checkpoint provavelmente está grande demais e deve ser quebrado. lifecycle-architecture-refactor não deve começar no PR #44 se não puder fechar nele.
Quem decide avanço? O PR é contêiner de review; o checkpoint mantém readiness própria; o Human Gate decide a entrega do PR/nó conforme escopo declarado. O PR body precisa listar claramente quais checkpoints foram entregues e quais continuam.
Como evitar outro CO-10.8.*? Checkpoints devem ter nomes semânticos, não numeração decimal interna. Sequência é atributo do nó, não parte do nome. Trocar CO-10.8.2 por lifecycle-model-inventory ou nome equivalente.
