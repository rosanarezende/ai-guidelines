Primeiro: qual é o seu cenário?

A experiência começa pela situação real do repositório. Assim o guia interativo não oferece comandos perigosos, não mistura caminhos e não força a pessoa a saber nomes internos do framework.

pasta nova

Quero iniciar um projeto

npm run flow -- init

Para uma pasta vazia ou um produto nascendo agora. O fluxo cria a base governada, pergunta as escolhas iniciais e mostra o plano antes de escrever.

  • Não mostra adopt/update como caminho principal.
  • Escolhas aparecem em grupos: IA, práticas e automações.
  • Dry-run deixa revisar tudo antes de aplicar.
repo existente

Quero adotar sem quebrar o que já existe

npm run flow -- adopt

Para um projeto que já tem arquivos, scripts e histórico. O fluxo preserva conteúdo, faz merge conservador e transforma conflito em decisão explícita.

  • Não trata o repositório como vazio.
  • Mostra o que será preservado, criado ou mesclado.
  • Conflitos exigem escolha humana antes de qualquer força.
repo governado

Quero usar e manter o framework

npm run flow

Para um repo que já usa ai-guidelines. O guia mostra estado, próxima ação, alternativas seguras, validações e updates possíveis.

  • Não mostra init/adopt como ação normal.
  • Update cobre runtime, templates, providers, features e práticas.
  • Specs seguem handoff, work, review, readiness, Ready, Gate e merge final.

Três caminhos, uma regra simples

O comando muda conforme o momento do repositório. O produto fica mais fácil quando cada caminho tem uma responsabilidade clara.

init

Nascer certo

Cria a governança inicial em um projeto novo.

  • nome e package manager;
  • providers e features;
  • Prettier, Husky, CI, Quality Gates, TDD e BDD quando escolhidos;
  • preview antes de aplicar.
adopt

Entrar com cuidado

Adiciona ai-guidelines a um repo que já tem vida própria.

  • preserva scripts e arquivos existentes;
  • detecta conflitos reais;
  • usa force e force-prettier apenas como decisão explícita;
  • termina com diff verificável.
update

Manter governado

Atualiza o que já existe sem recriar o projeto.

  • runtime e templates;
  • providers via update --providers;
  • features/práticas via update --features;
  • limpeza segura via --prune quando algo deixa de ser gerenciado;
  • perfil de colaboração e política de reviews quando governados.

Fluxo 1 — Inicializar um projeto novo

Aqui a pessoa quer sair de uma pasta vazia para um repositório com baseline, práticas e contexto pronto para humanos e IA.

passo a passo

O que acontece

começo limpo

O guia não oferece adopt/update como caminho principal.

Se a pasta está vazia, a ação natural é inicializar. Isso evita que a pessoa precise entender comandos antes de saber o estado do repo.

flow init
◇ Pasta vazia detectada ◆Inicializar um projeto governado ◇Adotar repo existente não se aplica aqui ◇Atualizar repo governado não se aplica aqui
identidade

Nome, pasta e package manager entram antes das práticas.

A pessoa define o básico do projeto primeiro. Isso evita misturar configuração de produto com escolha de ferramentas.

identidade do projeto
◇ Como este projeto deve nascer? ◆Nome: minha-api ◆Target: . ◆Package manager: npm ◇Esses valores entram no plano antes da escrita.
colaboração

O projeto já nasce com uma política humana explícita.

A pessoa escolhe se o repositório é solo, aberto a contribuições externas ou de time. Isso define expectativas de revisão e approvals sem mexer no código do produto.

perfil de colaboração
◇ Qual perfil de colaboração este repositório deve usar? ◆Solo — uma pessoa decide; sem approvals nativos obrigatórios ○Com contribuições externas — mais rastreio de findings ○Time — reviews e proteção mais fortes
seleções agrupadas

Escolhas aparecem por intenção, não por flag solta.

O Clack permite mostrar grupos com ajuda curta. A pessoa entende por que uma prática existe antes de selecioná-la.

selecionar práticas

preview

A pessoa vê exatamente o que será criado.

O plano mostra efeitos: arquivos, blocos gerenciados, scripts e comandos de instalação. O código que aplica as mudanças só executa o que o plano decidiu.

preview do plano
◇ Plano de inicialização

Práticas selecionadas aparecem como efeitos explícitos. +.github/workflows/ci.yml +.prettierrc + .prettierignore +.husky/pre-commit quando solicitado +quality-gates.md quando selecionado
Nada é instalado sem opção explícita e confirmação. =--dry-run mostra o plano sem escrita ?--install roda o package manager escolhido ?Confirmar antes de aplicar?
confirmação

Aplicar é uma escolha explícita.

O guia separa preview de aplicação. O humano confirma quando está confortável com o plano, e dry-run continua disponível para revisar sem efeito.

confirmar aplicação
◇ Aplicar este plano? ◆Sim, aplicar agora ○Rodar apenas em dry-run ○Voltar e alterar escolhas
tarefas visuais

Validação vira checklist acompanhado.

Etapas discretas usam lista de tarefas. Operações longas usam spinner. Saídas contínuas podem usar log por grupo.

validar
✓diff sem erro de espaço ✓format aplicado ◆build em execução ◇checks completos antes do Gate

Fluxo 2 — Adotar um projeto existente

Aqui a pessoa já tem um produto funcionando. O fluxo precisa ganhar confiança: preservar conteúdo, explicar conflitos e permitir avanço em blocos verificáveis.

passo a passo

O que acontece

diagnóstico

Antes de propor ação, o fluxo entende o repo.

Scripts, formatter, hooks, CI e arquivos governados viram entrada do plano. O código que aplica as mudanças não decide regra de negócio.

flow adopt
◇ Projeto existente detectado ✓package.json encontrado ✓scripts existentes preservados !formatter rival detectado
política preservada

Adoção também decide como o repo será colaborado.

Se já existe política governada, o fluxo altera só o perfil ativo. Se não existe, cria a baseline sem apagar decisões próprias do projeto.

perfil de colaboração
◇ Como este repo deve ser colaborado?
Perfil enxuto para repo mantido por uma pessoa. ◆Solo =sem approvals nativos obrigatórios
Perfil leve para contribuições externas com rastreio melhor. ◆Com contribuições externas =findings aceitos exigem resolução
Perfil mais forte para coordenação de equipe. ◆Time =approvals e proteção mais fortes
preservação

O padrão é adicionar sem apagar.

Blocos gerenciados permitem atualização futura. Conteúdo fora do bloco é tratado como propriedade do projeto.

plano conservador
◇ O que será feito +Adicionar bloco gerenciado em AGENTS.md +Espelhar templates faltantes =Manter scripts existentes
conflito explícito

Conflito não vira surpresa no diff.

Se uma decisão pode alterar comportamento do projeto, o fluxo mostra opções: manter, migrar com force ou sair para corrigir manualmente.

resolver conflito
▲ Formatter rival encontrado
Quando há formatter rival, o padrão é preservar e pedir decisão. ◆Manter configuração atual ○Migrar para Prettier com --force-prettier =force-prettier vale só para formatter rival ○Sair e corrigir manualmente
Hook incompatível não é sobrescrito sem autorização. !.husky/pre-commit já existe ◆Preservar hook atual ○Adicionar bloco gerenciado se suportado
Workflow existente entra no plano como input, não como surpresa. ✓.github/workflows detectado ◆Preservar workflow atual ○Atualizar com force depois do preview
aplicação controlada

O fluxo só aplica o que foi autorizado.

Adoção conservadora segue sem force. Quando force é necessário, o guia mostra a consequência antes de permitir a aplicação.

aplicar adoção
◇ Aplicação planejada
Primeiro a pessoa vê o plano sem tocar no disco. =Arquivos existentes ficam intactos ✓Preview mostra tudo que seria alterado
A aplicação padrão preserva conteúdo do projeto. ✓Preservar arquivos fora de blocos gerenciados ✓Adicionar apenas templates faltantes
Prune remove só artefatos gerenciados que deixaram de fazer parte da seleção. ◆Remover artefatos gerenciados que não fazem mais parte da seleção? =Não apaga código ou conteúdo próprio do projeto ✓Útil ao remover provider, template ou prática gerenciada
Force só aparece quando a consequência está clara. ◆Forçar Prettier mesmo se houver formatter rival? !Substituir configuração exige confirmação separada !O preview precisa nomear o arquivo afetado
evidência

O onboarding termina com algo revisável.

O fluxo orienta validação do diff, não apenas “deu certo”. Isso é o que permite adotar o framework em projetos já em uso.

validar adoção
✓dry-run comparado com aplicação real ✓conteúdo existente preservado ✓diff pronto para review

Fluxo 3 — Usar e manter um repo governado

Aqui o projeto já usa o framework. O guia vira a porta humana do dia a dia: mostra o estado, sugere o próximo passo, oferece alternativas úteis e deixa ações sensíveis protegidas.

passo a passo

O que acontece

estado situado

A primeira tela responde “onde estamos?”.

O resumo precisa ser legível no celular: agora, depois, o que já está ok, o que falta e qual decisão não pode ser executada ainda.

flow
◇ Estado atual Agora: CO-10.5 — UX e guia governado Depois: CO-10.6 — falsificação + Human Gate PR Draft · CI verde · tree limpa ◆Próxima ação: declarar readiness quando critérios passarem
orientação

Alternativas aparecem quando ajudam a decidir.

Se houver uma percepção recorrente, revisão recomendada ou validação útil, ela aparece como alternativa. Bloqueios aparecem dentro da ação bloqueada, não como lista abstrata.

menu humano
◇ O que você quer fazer?
A primeira opção acompanha o que o modelo governado recomenda. ◆Finalizar mudanças locais e validar ○Ver resumo completo do estado
Alternativas ajudam sem competir com a próxima ação. ○Ver percepções recorrentes que precisam de decisão ○Ver orientação de trabalho / handoff ○Ver tipos de revisão disponíveis
Ações sensíveis aparecem com motivo, sem botão de execução. ◇Human Gate: bloqueado por PR Draft ◇Merge: só depois do Gate e integração final
validação guiada

O guia diferencia validação do diff e validação completa.

Durante a implementação, a pessoa consegue limpar formatação e conferir o que mudou. Antes de Ready ou Gate, o fluxo pede a validação completa.

validar mudanças
◇ Como validar agora? ◆Validar apenas meu diff ○Corrigir formatação do diff e validar ◇Validação completa entra antes do Gate
revisão antes da decisão

O guia pode sugerir revisão sem transformar isso em bloqueio escondido.

Quando o risco justificar, a pessoa pode preparar uma revisão técnica, arquitetural ou de segurança antes do Human Gate.

tipos de revisão
◇ Que revisão preparar?
◆Auditoria técnica Verifica comportamento, testes, paridade e riscos de regressão.
◆Revisão arquitetural Confere bounded contexts, SSOT, dependências e separação de responsabilidades.
◆Revisão de segurança Procura risco em autoridade humana, comandos mutantes, stale state e permissões.
O texto fica pronto para copiar e colar na IA escolhida.

Repo governado usa update, não init/adopt.

Revisão pode ser sugerida antes do Gate.

Reviews opcionais reduzem risco, mas não viram bloqueio escondido. Reviews obrigatórios bloqueiam quando a política exigir.

Da primeira ideia ao merge final

O ai-guidelines é mais valioso quando uma spec inteira deixa de depender da memória de uma pessoa. Cada etapa tem entrada, autoridade, comando, efeito permitido, validação e próximo estado.

1 Nasce a spec Problema, escopo, topologia e checkpoints entram em artefatos governados.
2 PR Draft cedo O PR vira contêiner de trabalho; Draft não significa entrega pronta.
3 Handoff Nova sessão recebe fatos versionados para colar na LLM de preferência.
4 Implementação Sub-checkpoints limitam escopo, autoridade e validações.
5 Reviews Obrigatórios bloqueiam; opcionais podem ser sugeridos para reduzir risco.
6 Correções Finding, resolution, verification e disposition fecham o ciclo de review.
7 Readiness O fluxo declara que o ponto está pronto; não é edição manual solta.
8 Ready + Gate PR deixa Draft; Human Gate decide se o checkpoint pode avançar.
9 Próximo nó A stack continua sem merge isolado em main.
10 Merge final O PR de integração fecha a spec inteira.

Regras de negócio que o fluxo protege

O guia interativo não é uma segunda fonte de verdade. Ele só apresenta, em linguagem humana, o que o modelo governado já derivou.

Regra Como aparece para a pessoa O que evita
Uma próxima ação principal O menu destaca uma recomendação e move alternativas para baixo. Escolhas paralelas que parecem igualmente certas.
Ação bloqueada explica o motivo O bloqueio aparece dentro da ação: CI pendente, tree suja, PR Draft, finding aberto. Listas abstratas que obrigam a pessoa a investigar código.
Ação proibida não vira botão Ready, Human Gate, merge e transição de nó só aparecem quando o fluxo permite. Executar decisão humana por engano.
Providers não é comando próprio Provider selection aparece dentro de init/adopt/update. Voltar a um verbo legado depois do corte do runtime antigo.
Review opcional não bloqueia sozinho O guia pode sugerir revisão antes do Gate, mas diferencia recomendação de bloqueio. Transformar prudência em trava escondida.
Offline ou dado stale muda o estado Sem GitHub/CI confiável, o fluxo mostra modo degradado e impede decisões inseguras. Liberar Gate com PR, CI ou receipt desatualizado.

Por que desenvolvedores deveriam usar

O framework reduz trabalho invisível: menos decisões perdidas em chat, menos drift entre PR e artefatos, e menos risco de avançar no estado errado.

clareza

A pessoa sabe o que fazer agora

O guia responde “onde estamos?”, “o que falta?” e “qual comando usar?” sem exigir leitura de arquivos internos.

continuidade

Contexto viaja entre sessões

Handoff e work viram texto copiável para humanos e LLMs, mantendo a fonte factual no repositório.

controle

Automação não atropela autoridade humana

Ready, Human Gate, merge e mudanças sensíveis exigem estado correto, prévia e confirmação explícita.
